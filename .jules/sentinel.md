## 2024-05-18 - [Firestore Rules resource == null Bypass]
**Vulnerability:** A vulnerability existed in Firestore rules where `resource == null` was used inside shared write rules (`allow write`) for `/notifications/{notificationId}` and `/backups/{backupId}`. This allowed any authenticated user to create notifications and backups for *other* users, because during document creation, `resource` is null and this condition evaluates to true, completely bypassing the `resource.data.userId == request.auth.uid` check. Additionally, there was a redundant `allow create: if isAuthenticated();` on `/users/{userId}` that bypassed the write rule requiring the user to own the ID.
**Learning:** `resource` represents the existing document. When a document is created, `resource` is always null. If `resource == null` is used in an `allow write` block (which covers create, update, delete), it effectively makes document creation completely public to anyone meeting the other conditions (e.g. `isAuthenticated()`), ignoring the actual data being created (`request.resource.data`).
**Prevention:** In Firestore rules, always separate read/delete from create/update. For write operations that create or modify data, validate ownership strictly against `request.resource.data`. Never use `resource == null` as an OR condition to bypass ownership checks inside unified write blocks.
