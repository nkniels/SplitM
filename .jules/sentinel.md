## 2024-05-24 - [Firestore Rule Bypass via resource == null]
**Vulnerability:** A rule in `splitm-v2/firestore.rules` used `resource == null` combined with `resource.data.userId == request.auth.uid` for `allow write` access on `notifications` and `backups`. Since `resource` represents the existing document in Firestore, it is always `null` when a document is being created. This meant `resource == null` evaluated to true and fully bypassed the `resource.data.userId == request.auth.uid` check during document creation. Consequently, any authenticated user could create notification or backup documents pretending to be another user. Furthermore, the `users` collection allowed unrestricted user document creation.
**Learning:** In Firestore rules, `resource` is null during creation, and `request.resource` must be used to inspect the incoming document data. Using `allow write` (which includes both create and update) with checks relying solely on `resource.data` can inadvertently open up document creation to everyone if paired with a `resource == null` fallback.
**Prevention:** Always separate `allow read, delete` (where `resource.data` is valid) from `allow create, update` (where `request.resource.data` should be evaluated). Never use `resource == null` to conditionally bypass data validation checks during writes unless explicit creation rules follow.
