## 2024-11-21 - [CRITICAL] Fix Overly Permissive Firestore Rules
**Vulnerability:** The `splitm-v2/firestore.rules` file contained critically permissive rules, allowing any authenticated user to write/update/delete to all subcollections and root collections (`members`, `expenses`, `settlements`) without verifying group ownership.
**Learning:** The architectural flaw was not enforcing parent-child ownership relationships for mutations. While NoSQL databases may require broad read access for clients, mutations (create/update/delete) must be strictly constrained to authorized owners using cross-document checks (e.g., `isGroupOwner()`). Additionally, separating `read/delete` from `create/update` is necessary to prevent null reference bugs when evaluating `request.resource`.
**Prevention:** Always tie child collection mutations back to the parent entity's ownership using helper functions in Firestore rules (e.g., `isGroupOwner(groupId)` or `isGroupOwner(resource.data.groupId)`). Validate `request.resource.data` only on `create` and `update` actions, and ensure read operations do not erroneously evaluate mutation payloads.
